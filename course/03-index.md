# 3단계 — 문서 폴더를 조각내고 임베딩으로 찾기

## 왜 하나요

2단계에서는 정답 문서를 내가 골라 붙였어요. 실제로는 **질문에 맞는 부분을 프로그램이 찾아야** 해요. 문서 수백 편을 통째로 붙일 수는 없어서, 문서를 작은 조각으로 자르고 각 조각을 숫자(임베딩)로 바꿔 둔 뒤, 질문과 숫자가 가까운 조각을 찾아요.

| 말 | 쉬운 뜻 |
|---|---|
| 색인 | 조각과 그 숫자들을 미리 계산해 저장해 둔 것. 한 번 만들면 찾을 때마다 다시 계산하지 않아요 |
| 정규화 | 숫자 목록의 길이를 1로 맞추는 것. 그러면 두 목록을 곱해 더한 값(내적)이 바로 "얼마나 비슷한가"(코사인 유사도, 최대 1)가 돼요 |

먼저 짐작해서 적어요: "문서 말 그대로 묻는 질문 vs 일상 말로 바꿔 묻는 질문, 어느 쪽을 임베딩이 더 잘 찾을까?"

## 준비: 문서 폴더 복사

```sh
mkdir -p private/corpus
cp -R <내 문서 폴더> private/corpus/
```

- 원본 대신 복사본을 써요. 7단계에서 실험용 문서를 일부러 넣을 거예요

## 만들 것 1: `step3_index.py` (색인 만들기)

```text
3단계 색인 스크립트 step3_index.py 를 만들어줘.
- 실행: python3 step3_index.py --root <문서 루트> [--dirs 폴더 …] [--out private/index] [--dry-run]
  --dirs 를 안 주면 root 전체를 읽어
- 읽기: 대상 폴더 아래 모든 .md. 이름이 점(.)으로 시작하는 폴더는 건너뛰어
- 맨 위에 --- 로 감싼 frontmatter 가 있으면 title·keywords 값을 읽고 본문에서는 빼
- 조각내기:
  - 헤딩(# ~ ######) 단위로 잘라. 코드 블록(``` 사이) 안의 # 은 헤딩으로 보지 마
  - 헤딩 경로를 기억해 (예: "설치 > 맥에서 설치")
  - 본문이 20자 미만인 절은 버려
  - 1200자를 넘는 절은 빈 줄 단위 문단으로 나눠 1200자 이하로 묶어 (문단 하나가 1200자를 넘으면 1200자씩 잘라)
- 조각 앞머리: 본문 앞에 "문서: 제목\n키워드: …\n절: 헤딩 경로\n" 를 붙여 (없는 줄은 생략)
  제목은 frontmatter title → 첫 번째 "# " 줄 → 파일 경로 순으로 정해
- 조각 정보: {"path": root 기준 상대 경로, "line": 절이 시작하는 줄 번호, "heading": 헤딩 경로, "text": 앞머리 + 본문}
- --dry-run 이면 문서 수, 조각 수, 조각 글자 수(중앙값·90%·최대)만 출력하고 끝내
- 임베딩: http://127.0.0.1:11434/api/embed 에 model "bge-m3", input 에 조각 text 32개씩. 받은 벡터는 길이 1로 정규화
- 저장 (--out 폴더):
  - vectors.f32 = 모든 벡터를 float32 로 이어 붙인 바이너리 (array 모듈의 'f')
  - chunks.jsonl = 조각 정보 한 줄에 하나
  - meta.json = {model, dim, count, docs, seconds, max_chars, built}
- 조각 640개마다 진행 상황(개수, 걸린 초)을 출력해
- numpy 없이 표준 라이브러리만
```

## 만들 것 2: `step3_search.py` (찾기)

```text
3단계 찾기 스크립트 step3_search.py 를 만들어줘.
- 실행: python3 step3_search.py [-k 5] [--index private/index] "질문" ["질문" …]
  질문을 안 주면 private/step3_queries.json (["질문", …]) 을 써
- 다음 단계에서 import 해서 쓸 함수 두 개를 따로 만들어:
  - load_index(폴더) → (meta, chunks, rows)  rows 는 조각마다 벡터 하나
  - embed(model, text) → 길이 1로 정규화한 벡터
- 찾기: 질문을 meta 의 model 로 임베딩 → 모든 조각 벡터와 내적 → 큰 순서로 k 개
- 출력: 질문마다 걸린 초, 그리고 순위·점수(소수 3자리)·path:line·헤딩·본문 마지막 줄 80자
```

질문 5개를 `private/step3_queries.json` 에 써요.

| 종류 | 예 | 1회차 결과 (임베딩) |
|---|---|---|
| 문서 말 그대로 | 문서 제목의 단어를 쓴 질문 | 성공 |
| 일상 말로 바꿔 말함 | 같은 내용을 문서에 없는 말로 | **성공** (키워드 검색은 실패) |
| 숫자·코드 한 단어 | 문서에 나오는 오류 번호 하나만 | 실패 쪽 (숫자 많은 엉뚱한 목록 문서가 1·2위) |
| 짧은 불만형 | "자꾸 ○○가 안 돼요" | 3위에 관련 문서 |
| 문서 폴더에 없는 내용 | 내 문서 어디에도 없는 질문 | 실패 (찾을 게 없음) |

## 직접 실행

```sh
python3 step3_index.py --root private/corpus --dry-run     # 먼저 조각 수만 확인
python3 step3_index.py --root private/corpus               # 실제 색인 (1회차: 조각 6,855개에 689초)
python3 step3_search.py                                    # 질문 5개 찾기
python3 step3_search.py "직접 쳐 보는 질문"
```

- 색인 중에는 `ollama ps` 에 `bge-m3` 가 보여요

## 코드에서 꼭 읽을 곳

1. 조각 앞머리(문서·키워드·절)를 붙이는 부분 — 조각만 떼어 봐도 무엇에 대한 글인지 남기는 장치
2. 긴 절을 문단으로 나누는 함수 — 왜 1200자인가 (임베딩 모델이 한 번에 읽는 양, 답할 때 붙일 양)
3. 정규화 뒤 내적만 하는 찾기 — 왜 이게 "뜻이 가까운 정도"가 되나

## 고쳐 보기

| 바꿀 것 | 짐작 먼저 | 확인 |
|---|---|---|
| 1200자 → 400자, `--out private/index-400` 으로 새 색인 | 조각 수는? 찾기는 좋아질까? | `--dry-run` 조각 수, 같은 질문 5개를 `--index private/index-400` 으로 |
| 앞머리 빼기, `--out private/index-nohead` | 어떤 질문이 나빠질까? | 같은 질문 5개 비교 |

- 4단계 시험지로 이 색인들을 다시 채점하면 숫자로 비교할 수 있어요
