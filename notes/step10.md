# 10단계(응용) 정리 — 직접 만든 벡터 찾기 vs FAISS (2026-11-12)

## 왜

3~6단계의 벡터 찾기는 벡터 DB 없이 직접 만들었다: 길이를 1로 맞춘 벡터를 `vectors.f32` 에 저장하고, 질문 벡터와 조각 6,855개를 **전부 하나씩 내적**해서 큰 순으로 고른다. 실무에서 많이 쓰는 FAISS 로 바꾸면 무엇이 달라지는지 같은 시험지로 쟀다.

## 방법

- 설치: FAISS 최신판(`faiss-cpu 1.15.1`)은 Python 3.10 이상이 필요해 `python3.11 -m venv .venv`. 설치 파일(wheel)을 먼저 받아 지문 파일(`SHA256SUMS`)을 만들고, **밖으로 나가는 연결을 막은 샌드박스 안에서** `pip install --no-index --find-links <폴더>` 로 설치 (9단계 반입 연습과 같은 방식). 버전 = `setup/requirements-faiss.txt`
- 색인 (`faiss_store.py`) — 3단계 `vectors.f32` 를 그대로 읽어 만듦 (다시 임베딩하지 않음)
  - Flat (`IndexFlatIP`): 전부 비교. 지금 방식과 같은 결과여야 함
  - HNSW (`IndexHNSWFlat`, 내적): 이웃 그래프를 따라가는 근사 탐색. 설정 M=32·efConstruction=100·efSearch=64 는 흔히 쓰는 값으로 **미리 정하고 결과를 보고 바꾸지 않음**
- 비교 (`step10_faiss.py`) — 4단계 시험지 20문항으로 파이썬 전수 비교·numpy·FAISS Flat·FAISS HNSW 의 recall·찾기 시간·결과 일치
- RAG 전체 (`step6_rag.py --faiss hnsw`) — 6단계 22문항을 FAISS 검색으로 다시 돌려 기존 결과와 비교
- 규모 시험 — 실제 벡터 6,855개 + 실제 벡터에 잡음을 섞은 복제로 20만 개를 만들어 같은 질문 20개로 시간·메모리·HNSW 정확도

## 결과 (M1 Pro 16GB, 질문 1개씩)

6,855개 조각
| 방식 | 찾기 시간 중앙값 | 단어 겹침 @1 / @5 | 바꿔 말함 @1 / @5 | 파이썬과 문서 top5 같음 |
|---|---|---|---|---|
| 파이썬 전수 비교 (지금) | 243ms | 8 / 10 | 3 / 6 | — |
| numpy 행렬 곱 | 약 1ms (0.9~1.0) | 8 / 10 | 3 / 6 | 20/20 |
| FAISS Flat | 약 1ms (0.8~1.0) | 8 / 10 | 3 / 6 | 20/20 |
| FAISS HNSW | 0.3ms | 8 / 10 | 3 / 6 | 17/20 |

- 두 번 실행해 recall·일치 수는 같았고, 시간은 괄호 범위로 흔들림. numpy 와 Flat 은 이 규모에서 차이가 없다고 봄

- 질문 임베딩(bge-m3) 38ms — FAISS 를 쓰면 찾기보다 임베딩이 더 오래 걸린다
- HNSW 가 순서가 달랐던 3문항은 정답 순위도 20위 밖 근처에서만 달라짐 (P02 18위 → 20위 밖, P03 20위 밖 → 19위). recall@5 는 같음
- 색인 만들기: Flat 0.0초·28.1MB, HNSW 0.3초·29.9MB

RAG 전체 (6단계 22문항, `--faiss hnsw`)
| | 기존 (파이썬 전수 비교) | FAISS HNSW |
|---|---|---|
| 4칸 (찾기 성공·답함 / 찾기 실패·거절 / 찾기 실패·답함 / 답 없는 질문·답함) | 15 / 4 / 2 / 1 | 15 / 4 / 2 / 1 |
| 찾은 조각 5개가 같은 문항 | — | 21/22 (X2 만 5개 중 1개 다름, 칸은 같음) |
| 문항당 시간 중앙값 | 7.3초 | 7.5초 (답 쓰기가 대부분) |

20만 개 (실제 6,855 + 잡음 섞은 복제)
| 방식 | 찾기 1회 | 메모리 | 만들기 |
|---|---|---|---|
| 파이썬 전수 비교 | 약 7.1초 (6,855개 실측에서 비례 **추정**) | — | — |
| numpy | 79ms | 819MB | — |
| FAISS Flat | 24ms | 819MB | 0.7초 |
| FAISS HNSW | 8.7ms | 874MB | 25초 |

- HNSW 가 정확한 상위 10개(Flat) 중 찾은 비율 = 90.5%. 잡음 섞은 복제끼리 매우 비슷해서 근사 탐색에 불리한 데이터라 실제보다 낮게 나왔을 수 있음

## 배운 것

- 지금 규모(6,855개)에서 느렸던 건 **파이썬 for 문**이었다. numpy 행렬 곱 한 줄로 243ms → 1ms. FAISS Flat 도 비슷해서, 이 규모에선 FAISS 가 꼭 필요하지 않다
- FAISS Flat 은 지금 방식과 결과가 완전히 같다(20/20). 바꿔도 정확도 손해가 없다
- HNSW 는 빠르지만 근사라서 가끔 다른 조각을 고른다. 6,855개에선 recall·RAG 칸 모두 같았지만, 20만 개 잡음 데이터에선 상위 10개 중 9할만 맞췄다 → 쓰려면 Flat 과 비교한 정확도를 같이 재야 한다
- 규모가 커지면 차이가 벌어진다: 20만 개에서 파이썬 약 7초, numpy 79ms, HNSW 9ms. 수십만 개 이상·응답 시간이 중요할 때가 FAISS(HNSW 등)를 쓸 때
- 대신 의존성이 생긴다: Python 3.10 이상 + 설치 파일 3개(약 10MB). 분리망이면 이것도 반입 대상 — 설치 파일 지문 대조 + 인터넷 없이 설치로 확인했다
