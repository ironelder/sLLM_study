# 9단계(응용) 정리 — 분리망 가정 모델 옮기기 + 가상 VOC 처리 흐름 (2026-11-12)

## 왜

1~8단계는 문서를 찾아 답하는 RAG 였다. 실제 업무에 가까운 모양으로 넓혀 봤다: **인터넷이 없는 망(분리망)에 모델을 들여가서**, 고객 문의(VOC) 티켓을 읽고 → 그 고객의 로그를 찾고 → 개인정보를 가리고 → 요약해서 → 메일로 보내기.

## 실제로 한 것과 가정한 것

| 항목 | 이번에 한 것 | 실제 분리망·실서비스와 다른 점 |
|---|---|---|
| 모델 반입 | 모델 파일을 tar 하나로 묶고 sha256 지문 파일을 만든 뒤, 다른 폴더에 풀어 지문을 다시 대조 | 같은 Mac 안에서 폴더만 옮김. 보안 검수·망연계 전송 절차는 없음 |
| 인터넷 차단 | macOS 샌드박스(`setup/no-network.sb`)로 밖으로 나가는 연결을 막고 실행 + 사용자가 직접 Wi-Fi 를 끄고 실행 (`setup/offline-check.sh`, 11-13) | 진짜 분리망 장비가 아님 |
| Jira 티켓 | Jira 검색 API 응답 모양의 **가상** 티켓 6건 (`samples/voc/tickets.json`) | Jira 서버에 연결하지 않음 |
| 고객 로그 | **가상** 로그 31줄 (`samples/voc/logs.jsonl`). 회원번호·시간 범위로 찾기 | 실제 로그 저장소(검색 엔진·DB)가 아님 |
| 메일 | `.eml` 파일 저장 + 이 기기 안에서만 받는 시험용 SMTP 서버(`mail_sink.py`)로 발송 | 사내 메일 서버가 아님 |
| 모델 | `qwen3.5:4b` (답·해석·요약), `bge-m3` (임베딩, 이번 흐름에서는 동작 확인만) | 같음 |

## 방법

1. **모델 옮기기** (`setup/move_models.py`)
   - 묶기: 모델 목록표(manifest)가 가리키는 파일(blob)만 골라 tar 하나 + 지문 파일 `models.tar.sha256`
   - 풀기: ① 묶음 지문 대조 → ② 풀기 → ③ blob 마다 sha256 을 다시 계산해 파일 이름과 같은지 → ④ 목록표가 가리키는 blob 이 다 있는지
2. **옮긴 폴더로 서버 띄우기** — 원래 서버를 끄고 `OLLAMA_MODELS=<옮긴 폴더>` 로 같은 포트에 띄움. 빈 폴더로 띄우면 모델 0개(대조군) → 옮긴 폴더를 읽는다는 증거
3. **VOC 흐름** (`step9_voc.py`)
   - 회원번호·전화·이메일·이름은 **정규식**으로 뽑고, 모델에 넣기 **전에** 가림 → 요약·메일에 개인정보가 섞일 수 없는 구조
   - 해석(모델, JSON 칸 지정): 분류·증상·발생 시각·긴급도. 발생 시각은 "어제"·"월요일" 같은 말을 접수 시각 기준으로 계산하게 하고, 형식·범위가 틀리면 버림
   - 로그 조회(코드): 같은 회원번호 + (발생 시각 12시간 전 ~ 접수 시각). 발생 시각을 모르면 접수 72시간 전부터. 보관 기간 14일 밖이면 잘라서 조회하고 메일에 적음
   - 요약(모델, JSON 칸 지정): 요약(문장마다 `[L번호]`) → 원인 확인 여부(참/거짓) → 다음 조치
   - 자동 확인(코드): 인용 번호가 실제 로그 줄인지, 요약에 나온 오류 코드가 로그에 있는지, 메일 본문에 가리지 않은 개인정보가 남았는지
   - 메일: 제목 `[VOC-101] 결제 · 긴급도 높음 — VOC 요약(AI 초안)`, 본문 끝에 "AI 초안이니 원문 확인" 문구
4. **채점** (`samples/voc/expected.json`) — 분류, 발생 시각, 핵심 로그 인용, 회원번호 없음 처리, 원인 확인 여부

가상 티켓에 넣은 어려운 경우
- 회원번호가 없는 티켓 → 로그 조회를 건너뛰고 메일에 "회원번호 확인 필요"
- 회원번호는 있는데 문의한 문제의 로그가 없음 → 원인 확인 "아니요"가 정답
- 같은 시각에 **다른 고객**의 결제 실패 로그(다른 오류 코드) → 섞이면 안 됨

| 방법 | 크기 | 시간 |

- 지문 대조는 압축 여부와 상관없이 같은 방식으로 됨

- 발생 시각이 가장 약하다: "오후 3시쯤"을 00:00 으로, 날짜를 며칠씩 틀림. 시각 없이 날짜만 내 형식 검사에서 버려진 것도 1건. 틀린 날짜가 대부분 실제보다 **이른** 쪽이라 조회 범위가 넓어져 원인 로그는 13/14 를 찾았다 (늦은 쪽으로 틀리면 원인 로그를 놓친다)
- 분류 3건: 적립금 문의를 결제로, 현금영수증 문의를 앱 오류로, "결제하기 누르면 첫 화면" 문의를 앱 오류로 (마지막은 뜻으로는 틀렸다고 보기 어려움)
- 핵심 로그 1건: 원인이 두 줄(재고 동기화 실패 + 자동 취소 실패)인데 한 줄만 인용
- 이 20건도 이제 결과를 봤으니, 이걸 보고 고치면 다음 평가에는 또 새 티켓이 필요하다

## 실수 하나

- `offline-check.sh` 의 정리(원래 서버 다시 켜기)를 `trap … EXIT` 로 걸었는데, macOS `sh` 에서 파이프(`| tee`) 안 함수에 건 trap 은 불리지 않았다
- 그래서 처음 두 번은 오프라인 서버·메일 받는 쪽이 그대로 남았고, 다음 실행의 메일이 앞 실행의 받는 쪽으로 갔다 (새 받는 쪽은 포트가 이미 쓰여 실패)
- "서버가 떠 있다"만 보고 원래 서버로 돌아왔다고 판단했다가, 프로세스 환경변수(`OLLAMA_MODELS`)를 보고서야 오프라인 서버임을 알았다 → 정리를 파이프 밖에서 직접 부르고, 어느 폴더로 떴는지까지 확인

## 배운 것

- 식별자 추출·로그 조회·가림·검증은 **코드**, 해석·요약은 **모델** — 틀리면 안 되는 일은 모델에 맡기지 않는다
- 개인정보는 모델에 넣기 전에 가리면, 모델이 무엇을 쓰든 메일에 원문이 나갈 수 없다
- 4B 는 상대 날짜 계산("이번 주 월요일")이 약하다 — 새 20건에서 7/15. 조회 범위를 넉넉히 잡아 피해를 줄였지만, 날짜 계산은 코드로 하는 게 맞다
- 고칠 때 본 데이터로 잰 숫자는 부풀려진다: 6건에서 3/4 였던 발생 시각이 새 20건에서 7/15. 평가용 데이터는 고치는 사람이 보지 않은 것으로 따로 둔다
- 판단을 문장으로 받으면 채점이 흔들린다 → JSON 칸으로 받고, 칸 순서는 "근거 → 판단"
- 모델을 옮길 때는 묶음 지문 + 파일별 지문 두 겹으로 확인하고, 빈 폴더 대조군으로 "옮긴 폴더를 읽는다"를 증명한다
